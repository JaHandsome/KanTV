# PRD：IPTV NAS 常驻服务（iptv-nas）

## 0. 项目信息

| 项 | 内容 |
|---|---|
| 产品名称 | iptv-nas（NAS 常驻 IPTV 直播源服务） |
| 语言 | 中文 |
| 技术栈 | Python 3 纯标准库（http.server / sqlite3 / concurrent.futures），零第三方依赖，适配 NAS 环境 |
| 部署目标 | 用户 NAS（与电视同局域网），长期无人值守运行 |
| 原始需求 | 将已实测验证的单文件 IPTV 流水线脚本升级为 NAS 常驻服务：优化流水线、强化源发现、健康监控与容灾、以量带质、低资源长期运行 |

**现状基线**（来自现有脚本与实测数据）：
- 目标频道 85 个（CCTV1-17 / 省级卫视 / 广东本地 / 港澳台），当前实测仅部分频道有可用源，多数频道可用线路仅 1 条（冗余度不足，存在单点故障）。
- 现有脚本只有 `build` / `refresh` 两种一次性运行模式，无源发现、无自动容灾、无 HTTP 常驻服务。
- 已知死源规律：39.134 电信 IPTV 网关（永久不可达，需机顶盒认证）；vpstv / kylintv / fretv.fun（403/死亡）；t.061899.xyz（动态源，时通时断）。
- 网络限制：GitHub API 不可直连；jsDelivr CDN 可用、ghproxy 阶段性可用。

---

## 1. 产品目标

### 1.1 一句话愿景

把"手动跑脚本、看天吃饭"的 IPTV 源整理工作，变成一台 NAS 上**自动找源、自动验源、自动容灾、随时可看**的常驻服务——电视打开即看，用户无需干预。

### 1.2 可量化成功指标

| 指标 | 定义 | 目标值 |
|---|---|---|
| 可用频道数 | live.txt 中"当前至少 1 条实收验证视频源"的频道数 | ≥ 70 / 85（P0 阶段 ≥ 50） |
| 源冗余度 | 每频道可用线路数 ≥ 2 的频道占比 | ≥ 80% |
| 失效恢复时间（MTTR） | 单条源失效到该频道恢复可用（自动切换备用线路或新源）的时间 | ≤ 1 个刷新周期（目标 ≤ 30 分钟） |
| 源池规模 | 源发现层持续维护的"待验证候选 URL"总量 | ≥ 2000 条 |
| 新源接入时效 | 新源从被发现到完成验证入库的时间 | ≤ 24 小时 |
| 服务可用性 | HTTP 订阅接口（live.txt / live.m3u）月可用率 | ≥ 99%（本机进程视角） |
| 资源占用 | 常驻内存 / CPU | 见非功能需求 §4 |
| 无人值守度 | 连续 30 天无人工干预正常运行的达标率 | 100% |

**优先级原则（用户明确要求）**：源是项目根本——先数量与覆盖面，再质量，以量带质。P0 全部围绕"源够多、坏了能换、按时跑、能订阅"，质量排序与状态页属于 P1/P2。

## 2. 用户故事

### P0（Must have）

1. 作为家庭用户，我希望电视里 85 个目标频道**总有能看的线路**，所以服务要持续自动发现新源、扩充源池，单一源失效不影响观看。
2. 作为家庭用户，我希望 TVBox 里填一次订阅地址就**永远不用再改**，所以 NAS 上的 live.txt / live.m3u 要通过局域网 HTTP 常驻暴露，内容自动更新。
3. 作为家庭用户，我希望某条线路卡了/挂了系统能**自动切换到备用线路**，所以每频道要保留多条已验证线路（主备），失效源自动下线、恢复后自动重新纳入。
4. 作为家庭用户，我希望流水线**定时自动跑**而不是我手动执行，所以系统要按计划调度发现→验证→构建全流程。
5. 作为 NAS 的使用者，我希望这个服务**不拖垮 NAS 上其他服务**（相册、下载、虚拟机），所以要严格限制内存、CPU、并发连接数。

### P1（Should have）

6. 作为家庭用户，我希望换台时**首选线路尽量是画质好、延迟低的**，所以验证环节要记录响应质量（连接耗时、分片稳定性）并参与排序。
7. 作为有一定动手能力的用户，我希望出问题时**能自己排查**，所以要有一个简单的状态页（本机浏览器访问），看每频道每源的存活状态、最近变更历史。
8. 作为用户，我希望关键异常（如可用频道数跌破阈值、服务停止）能**主动通知我**，所以要有轻量告警通道。

### P2（Nice to have）

9. 作为用户，我希望**目标频道清单可以自助增删**（如新增一个地方台），所以频道配置要外置成易编辑的文件。
10. 作为用户，我希望知道服务运行得怎么样，所以要有运行统计（每天有效源数、发现/失效源数曲线类数据，简单文本/JSON 即可）。

## 3. 需求池

### P0：Must have（缺失则产品不成立）

| ID | 需求 | 说明 | 验收标准 |
|---|---|---|---|
| P0-1 | **自动源发现与扩充** | 内置源发现调度器，通过多通道持续抓取候选源清单：① 已知 GitHub 仓库清单（Guovin / suxuang / vbskycn 等）经 jsDelivr CDN 拉取原始 m3u/txt（`https://cdn.jsdelivr.net/gh/<user>/<repo>@<branch>/<path>`）；② ghproxy 镜像作为第二通道（可用性探测后启用）；③ 已验证的网关清单；④ 新源入库前统一去重（URL 归一化）。发现到的候选进入 sqlite 候选池等待验证 | ① 无人工干预运行 7 天，候选池总量 ≥ 2000 条；② 单通道（jsDelivr）失效时其余通道仍可独立供源；③ 重复 URL 入库率 = 0 |
| P0-2 | **候选源验证入库** | 对候选 URL 执行既有多级验证：HTTP 实连 → m3u8 逐级解析 → 分片实收 → 媒体级验证（TS PMT/PES、fMP4 盒、FLV tag），区分真视频/纯音频/垫片；结果写入 sqlite，含频道归属、验证时间、av 判定 | ① 验证结论与人工抽查一致率 ≥ 95%；② 垫片/纯音频不会被标记为可看源；③ 单次验证任务可中断续跑（中间结果落库） |
| P0-3 | **源健康监控与容灾** | 对已上线源周期性轻量探活（HEAD/首字节探测），维护每源健康状态（ok / flaky / dead）；频道线路表按健康度自动重排——失效源下线（移出 live 输出）、连续 N 个周期恢复则自动重新上线；探活结果与健康事件记入 sqlite 历史表便于排查 | ① 人为下线一条主线路后 ≤ 1 个刷新周期内 live.txt 中该频道切换到备用线路；② 被下线源恢复后 ≤ 2 个周期内自动回归；③ 每次状态变化在历史表中有记录（源、时间、原因） |
| P0-4 | **定时流水线调度** | 常驻调度器按计划执行全流程：源发现（如每 6h）→ 增量验证（如每 2h）→ 已上线源探活（如每 30min）→ 重建输出文件；周期可配置；任务互斥防重入 | ① 连续 7 天按计划自动执行，无人工触发；② 上一轮未完成时下一轮自动跳过/排队，不产生并发重复请求 |
| P0-5 | **TVBox 订阅输出（HTTP 常驻）** | 内置轻量 HTTP 服务（Python 标准库 http.server），暴露 `live.txt`、`live.m3u`、`tvbox_lives_snippet.json`；保持现有输出格式（分组、多线路 `#` 拼接、EPG 模板 `epg.51zmt.top`、台标模板 `gitee.com/suxuang/logo`）；文件更新采用原子替换，避免电视端读到半截文件 | ① 局域网内 TVBox 通过 `http://<NAS-IP>:<port>/live.txt` 订阅并正常播放；② 输出文件重建期间请求不返回残缺内容；③ 输出格式与现有脚本产物兼容（电视端零改动可继续使用） |
| P0-6 | **低资源运行与 NAS 适配** | 全流程 Python 3 标准库；并发与超时受控（网络并发上限、单请求超时、总任务时长上限）；日志落盘且自动滚动/清理；提供进程守护方式（systemd unit / Windows 计划任务 / NAS 计划任务任一即可，按用户 NAS 实际情况定） | ① 常驻内存 ≤ 200 MB，空闲 CPU ≤ 1%；② 验证高峰期 CPU 不持续打满单核；③ 日志磁盘占用有上限（如 ≤ 100 MB），无需人工清理 |

### P1：Should have（重要但可后置）

| ID | 需求 | 说明 | 验收标准 |
|---|---|---|---|
| P1-1 | 源质量评估与排序 | 探活时记录连接耗时、首字节时间、分片下载稳定性；频道线路按"视频已验证 > 质量分高"排序，质量分定期衰减重算 | 同频道多线路时，live.txt 首线路在质量分上优于备线路的比例 ≥ 70% |
| P1-2 | 状态页 | 本机/局域网浏览器访问的单页状态页（可由同一 HTTP 服务输出静态 HTML+JSON）：频道覆盖总览、每频道线路及健康度、最近失效/新增源、最近一次流水线运行结果 | 打开页面 3 秒内可见全部 85 频道覆盖状态；能定位"某频道为什么只剩 1 条线路" |
| P1-3 | 轻量告警 | 关键事件主动通知：可用频道数跌破阈值、服务异常退出、流水线连续失败 ≥ 2 轮；通道优先选用户已有的（如 Server酱 / Telegram Bot / SMTP，二选一即可） | 模拟"可用频道数跌破阈值"后 10 分钟内收到一条通知；通道不可达时告警记录不丢失 |
| P1-4 | 流水线性能优化 | 减少重复请求（同 URL 短 TTL 结果缓存）、增强解析容错（非标 m3u8、编码异常 URL）、失败重试与退避；全量验证一轮的耗时目标 | 增量刷新一轮（探活+局部验证）≤ 30 分钟；同 URL 24h 内不重复全量验证（结果缓存命中） |
| P1-5 | 死源规则库 | 沉淀已知死活规律为规则：39.134 网关段直接跳过不测、vpstv/kylintv/freetv.fun 域名拉黑、t.061899.xyz 标记为 flaky 降低探活权重；规则外置可编辑 | 规则库中的死源 0 次进入验证队列；新增黑名单域名无需改代码 |

### P2：Nice to have

| ID | 需求 | 说明 | 验收标准 |
|---|---|---|---|
| P2-1 | 频道清单外置配置 | 85 目标频道、分组、排序改为配置文件（JSON/文本），用户可增删 | 修改配置后下一个周期生效，无需改代码 |
| P2-2 | 运行统计报表 | 每日汇总：候选池规模、新增验证源、失效源、可用频道数，存 sqlite 并在状态页展示近 30 天趋势 | 状态页可查看近 30 天可用频道数变化 |
| P2-3 | 升级与备份 | 一键升级（拉取新版本脚本并平滑重启）；sqlite 数据定期备份 | 升级后历史数据保留；备份文件可手动恢复 |

## 4. 非功能需求

| 类别 | 要求 |
|---|---|
| 资源占用上限 | 常驻内存 ≤ 200 MB；空闲 CPU ≤ 1%；网络并发连接 ≤ 16（可配置）；峰值 CPU 不持续占满单核 |
| 依赖约束 | Python 3.8+ 纯标准库，零 pip 依赖；数据存储用 sqlite3 单文件；无外部数据库/消息队列 |
| 无人值守 | 断网/单源全挂等外部异常不得导致进程退出；所有网络操作有超时；异常自动重试 + 退避；日志滚动自动清理 |
| 网络环境适配 | 默认经 jsDelivr CDN 访问 GitHub 仓库内容；ghproxy 等镜像可用性自动探测；所有外网请求失败不影响本机 HTTP 订阅服务可用性 |
| 升级方式 | 目录化部署（代码 + data + 配置分离），升级 = 替换代码目录 + 重启进程，sqlite 数据跨版本保留；提供当前版本号查询 |
| 安全性 | HTTP 服务仅监听局域网地址（默认 0.0.0.0 可配置为内网 IP），无写操作接口；不暴露管理端口到公网 |
| 可观测性 | 全部关键动作写日志（发现/验证/上下线/构建），保留 ≥ 30 天；sqlite 保留状态变更历史 ≥ 90 天 |

## 5. 待确认问题

**给用户：**

1. NAS 的具体型号/系统（群晖 DSM？威联通 QTS？Debian/OMV？Windows？）——决定进程守护方式（systemd / 计划任务 / Docker）与 Python 版本基线。
2. NAS 的固定局域网 IP 是多少？HTTP 服务想用哪个端口（现有片段写的是 `192.168.1.10:8420`，是否沿用）？
3. 告警通道（P1）你现有什么可用：Server酱 / Telegram / 邮件 / 其他？
4. 可接受的每日外网流量消耗量级？（源发现+验证会产生持续外网请求，需确认无运营商流量顾虑）
5. 85 个目标频道清单是否需要现在就调整（增删频道），还是沿用现有清单？
6. 探活/刷新周期偏好：默认"探活 30min、增量验证 2h、源发现 6h"是否符合你的观看习惯（如晚上高峰前刷新一次）？

**给架构师：**

7. 源发现通道的深度：除 jsDelivr 拉已知仓库外，是否要设计"仓库清单本身的自动发现"（如从聚合仓库的 README/订阅列表中递归挖掘新仓库）？建议 P0 只做固定清单 + jsDelivr，递归挖掘放 P1。
8. sqlite 表结构归属：候选池、验证结果、健康历史三域是否分库/分表，由架构师定；但需满足"升级保留数据"。
9. 探活与全量验证的资源争用策略：是否允许探活任务与验证任务并行，还是统一排队？（倾向排队，简化互斥）
10. HTTP 服务与调度器是否同进程（单进程多线程）还是双进程？倾向单进程降低资源占用，由架构师评估 http.server 线程模型与长任务的隔离方案。
