# 看电视：深层播放策略补充清单

> 当前播放稳定基线为已验收的 **0.2.40（53）**，见 [基线记录](PLAYBACK_STABILITY.md)。后续播放变更遵守 [项目对照规则](../AGENTS.md#已验收的播放稳定基线)，下文历史研究计划不构成增加监测或替换稳定版的授权。

> **状态：历史研究记录（2026-09-28 标注）** —— 下文“最新实现/最新验收”描述的 LibVLC 双内核与连续 TS 预取路线已整体移除；当前客户端为 Media3 单内核 + GeckoView 镜像。策略清单本身仍可作为后续完善的参考。

后续进展：已下载 Kodi 21.3、三个 Omega 插件和 Media3 1.11.0 源码，具体调用位置、机制和内核复用判断见 [源码分析](kodi-source-analysis.md)。本文保留最初的候选总清单，不将分析完成等同于实现或播放验收。

最新评估：明确 Media3 与其中的 ExoPlayer 的关系，排除旧独立 ExoPlayer 新建路线，给出按故障分类、会话隔离与统一恢复预算的 [实施方案](media3-exoplayer-evaluation.md)。试验参数清单为待运行计划，不是性能结论。

最新实测：当前 70 个源已分别完成 Media3、LibVLC 和 Mac FFmpeg 批量检查。Media3 在模拟器上大量出现首帧后静止，LibVLC 明显改善但不能覆盖所有源（2026-09-08 的 70 源审计明细属一次性交接文档，已删除）。

最新实现：播放器不再按频道名称固定内核，而是根据首帧、视频帧持续推进、错误类型和当前设备的历史成功结果自动选择，设计与边界见[通用播放内核识别与学习](adaptive-playback-routing.md)。

最新验收：安全日志确认翡翠台的模拟器硬件解码停在首帧，直接 HLS 软件解码又因下载追不上播放而周期性耗尽缓存。当前候选改为 LibVLC FFmpeg 软件解码，并对适用的 MPEG-TS HLS 并行预取后输出连续 TS；Mac 模拟器已持续推进画面超过 157 秒。此前 70 源整表结果是在该策略完成前取得，属于历史结果，最终策略尚未重跑整表。

日期：2026-09-08。状态：研究与建议；用户要求先列出需要补充的内容，不把下列参数、切换策略或后台服务当成已批准实施。

## 已确认的方向

- 同时参考 TiviMate 和 Kodi。TiviMate 用于观察实际电视体验；Kodi 的官方源码、IPTV Simple 与 InputStream 文档用于理解可审阅的机制。
- 完全从零实现 kantv 应用，不复用 StreamTV 实现。应用从零开始不代表自行发明视频编解码算法，可以集成成熟的开源内核。
- 现有交互暂按原型继续。底部控制栏出现时返回先关闭浮层，继续全屏；再次返回才到节目表。
- 普通观看不显示技术面板。诊断数据放设置且脱敏。

## 哪些是事实，哪些还只是推测

| 结论 | 证据等级 |
|---|---|
| 本轮 TiviMate 5.3.3 APK 包含 Media3/ExoPlayer 类和 FFmpeg JNI 等依赖 | 已检查本地样本；依赖存在不能证明具体使用方式 |
| TiviMate 的缓冲阈值、内核选择、异常码流容错、预连接和设备黑名单策略 | 未获得完整实现；不能声称已经还原 |
| 用户觉得 TiviMate 比所用 OK 影视更流畅 | 有效的用户体验反馈；尚无控制变量测试，不能确定因果 |
| OK 影视具体版本、所选内核、配置、实际解析到的线路 | 未提供，不能按产品名称推断 |
| Kodi 将不同窗口的遥控动作分开定义；IPTV Simple 提供 M3U/EPG/回看等集成，InputStream 插件处理不同流输入 | 可由官方代码和插件文档核实 [K1–K4] |
| TiviMate 预先转码了用户的直播源，或者一定比所有播放器强 | 无证据，不采用此结论 |

## 流畅播放要补充什么

下表是 kantv 建议能力，不是对 TiviMate 内部实现的断言。P2=基础可安装版，P3=完善频道管理，P4=兼容与稳定性，P5=高级能力。

| 能力 | 用普通话解释 | 建议实现原则 | 代价/限制 | 阶段与验收 |
|---|---|---|---|---|
| 1. 正确识别源 | 频道列表只是目录，实际视频可能是 HLS 分片或连续 TS | 结合元数据、响应类型与实际内容选输入器，不单看扩展名；把直播、点播、回看分开 | 错误分类会影响时间轴、暂停和重连 | P2：无后缀、重定向、M3U/媒体清单混淆的样例都验证 |
| 2. 请求兼容 | 同一地址也可能需要特定请求头或经过跳转 | 按来源保存必要请求配置；限制重试和超时；日志去掉凭据；不能把认证失败无限重试 | 不擅自刷新账号/密钥或对外传递认证头 | P2：200/重定向/401/403/404/超时各走不同恢复路径 |
| 3. 首次缓冲与卡顿后缓冲 | 第一次开始看和断续后的重新播放，需要不同的准备量 | 分开配置启动、卡顿后恢复、持续缓冲的门槛；先测稳定性再调快 [M1] | 准备多会增加等待；缓冲占内存，长期吞吐不足依旧会卡 | P2：记录首帧、卡顿次数/总时长、恢复后再次卡顿率 |
| 4. 与直播前沿保持距离 | 比现场稍晚一点，可以给网络抖动留余量 | 对有直播窗口的 HLS/DASH 使用合理目标偏移；窗口过期后回到可用位置 [M2] | 稳定性和延迟有取舍；连续 TS 不照搬自适应直播窗口参数 | P2/P4：弱网、暂停太久、失效分片与窗口追赶测试 |
| 5. 换台过程控制 | 连续按几次后，只播放最后选中的频道 | 取消旧请求，以播放会话编号隔离过期结果；旧解码回调不能覆盖新频道；避免 UI 每次展开都重建播放器 | 解码器重用并非所有编码切换都安全 | P2：快速连续选择、往返切台，无错台/双音轨/黑屏残留 |
| 6. 预连接与有限预加载 | 在用户真正切过去前先准备一点 | 先评估 DNS/连接重用和频道元数据准备；只有源允许并发且实测有效时才考虑预拉另一频道 | 会占带宽和连接名额，可能使当前播放更差；首期不默认双路拉流 | P4：对照预加载开/关的首帧、当前频道卡顿和连接数 |
| 7. 等待可解码画面与容错 | 收到数据不一定马上能拼出完整图像 | 区分网络没数据、在等关键帧、码流结构异常；TS 容错选项只针对证实的样例使用 [M3] | 容错增加 CPU 成本，也可能短暂出现坏画面；不能制造缺失数据 | P2诊断/P4兼容：长关键帧间隔、缺 AUD/IDR 等可控样例 |
| 8. 解码器与设备适配 | 同一种视频，两台设备不一定适合相同解码方式 | 优先设备硬解；记录实际解码器、错误、掉帧；针对明确故障做候选回退与设备配置 [M4] | 软件解码可能发热、耗电、跑不动；“有 FFmpeg”不代表全视频软解 | P2基础/P4回退：两设备分别测 H.264/H.265、分辨率、帧率组合 |
| 9. 音频输出与音画同步 | 有画无声、回声、声音领先和视频卡顿要分开诊断 | 先普通解码输出；按实际音频格式和输出设备处理；透传单独验证；重连后重新建立同步 | 软件音频扩展需实际集成；不把视频重启当作所有音频问题的修复 | P4：切台、音轨切换、长播、断网后唇音/拍手同步 |
| 10. 帧率、刷新率和隔行视频 | 网络不卡也可能看起来一顿一顿，体育节目尤其明显 | 区分下载停顿、解码掉帧、显示节奏不均；1080i、50场/秒、25帧/秒与1080p/50帧分别标记 | 刷新率切换可能黑屏；去隔行能力依赖设备；不强制所有源统一60Hz | P4：运动画面、字幕横移、25/50与30/60、隔行源实测 |
| 11. 自适应清晰度 | 网络变差时是否能自动改看低一档 | 只在源确实提供多码率版本时启用自适应，避免频繁上下跳；单码率源不能凭空降码率 [M5] | 清晰度和稳定性权衡；用户需决定是否允许自动降低清晰度 | P4：限速时切档、恢复、音画连续性与实际分辨率 |
| 12. 有边界的自动恢复 | 出问题后自己尝试恢复，但不能无限转圈 | 区分网络断开、服务错误、直播窗口过期、解码失败；合理退避；取消旧重试；稳定后清零 | 错误类型需要可靠证据，不能靠一个定时器不断重启 | P2：断网/恢复、长时间无帧、服务器恢复后可继续；错误提示可操作 |
| 13. 同频道备用线路 | 主线路失效时尝试同一个频道的备用源 | 仅用用户提供且身份匹配的备用线路；记录冷却状态，防止两条坏线反复切换 | 时延、画质、音轨可能不同；不能把名字相似误当同一节目 | P3/P4：故障切换、恢复策略、频道与节目一致性 |
| 14. UI 与播放生命周期分离 | 打开设置或控制条不应把视频重新打开一次 | UI 焦点与播放器状态分离；返回关闭最上层；明确主页、锁屏/待机和应用退出释放策略 | 后台继续播放与前台重建要有清楚边界 | P2：浮层反复开关，频道及播放会话不变；恢复重进不双重播放 |
| 15. 配置持久化 | 好用的设置不用每天重设 | 稳定频道标识关联上次频道、排序、音轨偏好；列表刷新不覆盖用户设置 | 地址更新和频道删除需迁移/兜底，不能把短期签名地址当永久 ID | P2/P3：重启、系统回收、列表刷新、频道删除后的行为 |
| 16. 长时间资源控制 | 播放两小时和换台一百次后仍正常 | 控制内存/连接/线程/磁盘缓存上限，正确释放解码器，不让 EPG 更新占住播放线程 | 需要真机长播与温度观察，短时模拟器不能代替 | P2持续/P4完整：内存曲线、连接数量、温度、掉帧和崩溃 |
| 17. 本地诊断与对照 | 知道到底卡在哪一步 | 记录首帧、缓冲、加载、掉帧、音频欠载、解码器、实际轨道；匿名会话 ID；详细信息仅设置可见 | 黑盒参考应用读不到同等内部指标，只比较可观测数据 | P2：每次恢复可解释，敏感地址/凭据不进入报告 |
| 18. 回看、时移、录制 | 三种能力使用不同的数据和存储方式 | 回看服务、持续环形缓存、持久录制分别设计；参考 Kodi 插件的职责划分 [K2–K4] | 源授权、后台运行、存储与并发要求不同 | P5：按总功能清单独立验收，不能互相冒充 |

## “预先处理数据”具体指什么

1. **整理频道目录和节目单**：清洗名称、分组、ID、EPG 匹配。这改善选台体验，通常不会修复视频帧或长期带宽不足。
2. **播放器本地准备与缓冲**：打开连接、识别格式、解析时间戳、等关键帧、解码排队、准备若干秒数据。能够影响首播和抗抖动，是 kantv 首期应做好的部分。
3. **源服务/CDN 提前处理**：上游编码、分片和分发质量会影响播放；需要控制实际源和网络才能判断。
4. **代理或重封装**：把已有音视频重新装成合适的 TS/HLS 等封装，必要时处理时间戳；无法保证修复缺失媒体或不支持的编码。
5. **转码**：重新编码为设备更容易播放的格式，可降低码率或改变帧率；需要计算资源，可能增加延迟和损失画质。

本轮没有证据表明 TiviMate 做了第 4/5 项的服务端处理。kantv 首期建议直连播放；NAS 代理、重封装和转码只有出现可复现需求时另列方案与资源评估，不在当前范围实施。

## 内核建议与公平比较

- 当前 kantv 已接入 Media3，并完成 LibVLC 兼容路径试验。模拟器整表结果只能比较软件路径，尚不能代表两台目标真机的最终性能。
- 建议以 AndroidX Media3/ExoPlayer 开始，独立实现 UI 和播放策略；它公开支持缓冲门槛、直播窗口处理和设备解码。[M1–M4]
- Media3 提供的软件解码扩展需要手动集成；其官方 FFmpeg 模块主要提供音频格式解码，不代表安装一个扩展就有通用 H.264/H.265 4K 软件视频解码。[M4]
- 先用两台设备和用户实际源证明需求，再决定是否增加其他开源内核或服务端方案；不把“默认堆多个内核”当成流畅保证。

建议比较 TiviMate、Kodi（记录 PVR/InputStream 配置）、用户实际使用的 OK 影视（版本/所选内核待提供）与 kantv。使用同一设备、同一有效源、同一画质/音轨、相同网络和相近时间，轮换顺序做多次顺序测试；并发上限不明时不同时多开。不要只比较频道名字，实际线路可能不同。

记录：首次出画面中位数和较慢样本；换台时间与失败；缓冲总时长和次数；实际分辨率/帧率/解码器；音画同步；连续播放；断网恢复。参考应用无法读取内部指标时写“不可观测”，不编造相同口径。合成样例适合复现问题，不替代真实直播。

## 真正需要用户决定的体验取舍（目前仅建议）

| 事项 | 建议默认 | 何时再决定 |
|---|---|---|
| 直播延迟与稳定性 | 家庭观看优先稳定，允许适度落后现场 | 有真实源后展示实测差异，不先承诺具体秒数 |
| 自动降清晰度 | 先保持源默认选择；支持多码率时提供可控选项 | 发现清晰度/卡顿明显取舍时 |
| 刷新率自动切换 | 先不主动切换，避免每次换台屏幕闪黑 | 运动画面节奏问题确认后 |
| 自动备用线路 | 先只使用用户配置的同频道线路 | 用户提供备用源时 |
| 视频预加载与 NAS 处理 | 首期不增加后台多路拉流和 NAS 处理 | 确认有收益且设备/源条件允许时 |

以上不要求用户现在重复确认，先纳入方案与验收清单。

## 官方依据

- M1：[Media3 DefaultLoadControl.Builder](https://developer.android.com/reference/androidx/media3/exoplayer/DefaultLoadControl.Builder) — 启动、重新缓冲及缓冲容量配置。

- K1：[Kodi 默认遥控键位源码](https://github.com/xbmc/xbmc/blob/master/system/keymaps/remote.xml) — FullscreenLiveTV、VideoOSD 等窗口分别映射动作；具体效果还取决于版本、皮肤和配置。
- K2：[Kodi PVR 官方说明](https://kodi.wiki/view/PVR) — 直播/节目单/录制系统及客户端和后端职责。
- K3：[Kodi IPTV Simple 官方文档](https://github.com/kodi-pvr/pvr.iptvsimple/blob/Piers/README.md) — M3U/XMLTV、回看字段、输入插件与时移设置。
- K4：[Kodi InputStream FFmpeg Direct 官方仓库](https://github.com/xbmc/inputstream.ffmpegdirect) — 连续媒体输入、回看窗口与时移支持。
