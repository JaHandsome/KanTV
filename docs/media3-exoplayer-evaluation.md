# Media3 / ExoPlayer 评估与 kantv 播放方案

日期：2026-09-08。结论层级：官方资料与源码评估完成；尚未集成、编译或实测播放。本文将参考研究落实为第一版工程方案，不宣称已实现或已达到参考产品的流畅度。

## 选型结论

建议第一版采用 **AndroidX Media3 中的 ExoPlayer**，源码评估基线为 1.11.0。它能以标准 Android 依赖接入原创电视界面，缓冲、直播时间线、分片下载、音视频渲染和统计都有可用扩展点。最终是否覆盖两台目标设备的实际源，需要播放样机验证。

| 名称 | 实际关系 | kantv 判断 |
|---|---|---|
| Media3 | Android 媒体组件体系，包括播放接口、ExoPlayer、媒体会话、UI 等模块 | 选用所需模块，不引入与直播无关的整套功能 |
| Media3 ExoPlayer | Media3 中的播放器实现，包名 androidx.media3.exoplayer | 第一版候选内核，不需和“Media3”再做两套性能对照 |
| 旧独立 ExoPlayer | com.google.android.exoplayer2；最后版本 2.19.1，官方声明不再发布，2024-04-03 起停止向 dev-v2 提交 | 不用于从零新建的 kantv；无需为证明新旧性能高下先花时间搭一套旧工程 |

依据：[Media3 官方关系说明](https://developer.android.com/media/media3/exoplayer)、[旧 ExoPlayer 官方迁移公告](https://github.com/google/ExoPlayer)、[Media3 发布页](https://developer.android.com/jetpack/androidx/releases/media3)。2026-09-08 查询稳定版为 1.11.0；本地标签源码已冻结在 `reference/media3/media-1.11.0/`，不自动跟随开发分支。

初始依赖范围：media3-exoplayer、media3-exoplayer-hls、media3-ui；媒体会话按生命周期需求加入，DASH/RTSP 根据真实源协议加入。应用读取 M3U 频道目录、XMLTV 和台标；ExoPlayer 播放导入后选中的媒体地址。不能把“能播放 HLS 的 m3u8”当作“已实现 IPTV 频道列表导入”。

本地 `gradle/libs.versions.toml:7` 的 minSdkVersion 为 23，即 Android 6.0 基线。两台设备实际系统版本仍待读取，型号不能替代兼容检查。APK 包体、内存和启动表现暂未测量。

## 能力与缺口

| 能力 | 已有组件 | kantv 还需完成 | 判定 |
|---|---|---|---|
| 普通 HLS / HTTP TS 直播 | HlsMediaSource、ProgressiveMediaSource、提取器、播放器 | 正确识别协议、源级请求头、重定向、取消与超时策略 | 适合作为首期主线；实际编码是否能解取决于设备 |
| 首播与卡顿后恢复 | DefaultLoadControl 分别控制首播、再缓冲与继续加载 | 区分网络慢、等关键帧、解码失败，按源测试参数 | 可直接利用，不能只调一个“大缓存” |
| 直播时间线与延迟 | MediaItem.LiveConfiguration、DefaultLivePlaybackSpeedControl | 尊重源直播窗口，落后窗口时分类恢复 | 适用于有直播窗口的自适应源；普通直出 TS 没有同样窗口 |
| 自动清晰度 | TrackSelector 与码率自适应 | 尊重设备能力与用户偏好 | 只能在源已提供的档位中选择，不会生成新清晰度 |
| 硬件解码 | MediaCodec 渲染路径，可尝试其他已列出的解码器 | 设备/格式兼容记录、错误分类与合理回退 | 不保证任意电视支持任意编码 |
| 全面软件视频解码 | 官方 FFmpeg 扩展针对音频；另有特定格式视频扩展 | 若实际源需要额外软件视频解码，需独立工程评估 | 不声称一个 FFmpeg 扩展就获得 Kodi 全套视频软解 |
| 音画同步与帧节奏 | 播放时钟、音频输出、视频渲染与刷新率相关接口 | 音频直通、1080i、50fps、HDR、电视系统适配 | 代码能力存在，设备效果未测 |
| 快速连续换台 | 支持替换媒体项、停止、取消加载、复用播放器 | 去除过期请求与回调、保证最终选择优先、保存正确频道 | 属于应用工程，不能依赖默认 UI 自动处理 |
| 回看/暂停/时移/录制 | 可播放支持的历史媒体或窗口内内容 | 源回看协议、本地时移缓存、录制与预约系统 | 保留 P5 总清单；不是接入 ExoPlayer 后全部自动具备 |
| EPG、收藏、台标、分组 | 非播放内核职责 | 本地目录、更新、匹配、缓存、焦点管理 | 与播放独立，资料失败不阻止看电视 |

格式依据：[官方支持范围](https://developer.android.com/media/media3/exoplayer/supported-formats)。不要把 TS、HLS 等容器/传输支持等同于 H.264、HEVC 等编码均可解。RTSP、组播和特殊协议需要单独核对，不用一句“支持直播”概括。

## 吸收哪些 Kodi 思路

此前已经定位的 Kodi 文件、函数与版本见 [Kodi 源码分析](kodi-source-analysis.md)。这里给出实际落地方式。

| Kodi 已读机制 | kantv 的实现方式 | 避免的问题 | 验收 |
|---|---|---|---|
| 区分输入路径与流类型 | `SourceResolver` 生成协议、MIME、请求头和能力描述，再交给对应 MediaSource | 所有网址都当 HLS，或无后缀地址选错路径 | HTTP TS / HLS / 无后缀 / 重定向样例各通过 |
| 缓冲状态分阶段处理 | 优先使用 Media3 LoadControl；首播、再缓冲各自调节 | 为少卡顿无限增加起播等待 | 首帧、卡顿时长、直播延迟同时报告 |
| 时间戳与音画连续性处理 | 首先使用 Media3 提取与渲染机制；有证据的异常源再做针对性适配 | 把 Kodi 的 PTS 修正公式套到另一套时间线，造成二次校正 | 合成时间戳跳变/分片切换测试，不出现持续音画错位 |
| 分层拆包与解码，允许时再回退 | 硬件路径优先，失败后尝试已支持的候选；额外软解作为独立能力 | 无限制尝试同一失败解码器；把缺解码器误认为网络慢 | 区分不支持、初始化失败和解码过程错误 |
| 停止时中断输入与处理线程 | 全部换台由 `PlaybackCoordinator` 串行管理，会话编号隔离旧事件 | 快速换台后旧频道覆盖画面/提示，连接不断累积 | 30 次连续选台，最终选择始终正确 |
| 分片错误、字幕缺片等分类处理 | 自定义 `LoadErrorHandlingPolicy`，应用统一恢复预算 | 一点字幕问题反复重开整个频道；底层和上层轮流无限重试 | 模拟断片、字幕缺失、超时、403、断网 |
| 资源管理与后台工作分离 | 播放优先；节目单/台标更新限制并发并缓存；时移另做存储预算 | 导入大节目单挤占播放资源 | 播放期间更新资料，不出现焦点冻结或明显播放回归 |

这里吸收处理问题的方法，主要通过 Media3 已有接口实现；首期不移植 Kodi 的播放器主循环或改写 Media3 时钟。

## 吸收哪些 TiviMate 思路

证据分为实际观察、用户要求和未知。实际观察基于本项目已有官方 APK 与合成频道实验；不是本轮新增真机测试。

| 内容 | 证据性质 | kantv 采用方式 |
|---|---|---|
| 浏览频道与全屏观看围绕同一播放内容展开 | 原版已观察到列表、节目表预览与全屏的层级 | 频道侧栏、设置浮层不主动重建播放器；已有画面持续播放作为验收目标 |
| 节目表可预览，再进入全屏 | 原版合成频道观察 | 将预览/全屏作为同一播放会话的展示变化；避免切换布局就重新拉流 |
| 源与详细选项集中在设置 | 原版设置组织已观察；用户强调简洁 | 老人日常只选台；网络、解码、重试详情在设置 |
| 启动恢复上次频道、确认开列表、返回先关底部栏 | 用户已明确指定 | 直接作为 kantv 操作契约，优先于原版差异 |
| 多数直播看起来更流畅 | 用户实际感受；本项目还没有同源量化比较 | 作为验收参照，必须同时测延迟、卡顿、换台和音画 |
| 邻台预拉、特殊缓存值、智能转码、完整内部恢复逻辑 | 受保护源码无法确认 | 不虚构为已知 TiviMate 技术，也不据此照抄配置 |

我们能复制的是可验证的体验目标并自己实现；不能把“包里存在 Media3”推断成“使用最新版默认配置”或“已经掌握全部私有优化”。

## 代码结构与恢复契约

以下是待实现的责任划分，不是已存在的模块：

- `ChannelRepository`：播放列表、稳定频道标识、收藏、当前选台和上次成功播放的频道。
- `SourceResolver`：根据当前频道解析本次播放地址与请求条件；不将带时效凭据的旧 URL 当作频道身份。
- `PlaybackCoordinator`：唯一操作播放器的入口，处理选台、停止、恢复预算和应用生命周期。
- `Media3PlaybackEngine`：组装 MediaSource、LoadControl、TrackSelector、Renderers 与监听；向上报告结构化事件。
- `PlaybackDiagnostics`：仅保存脱敏编号、会话号、时间、状态与错误分类。不开启会输出真实 URI/请求头的通用完整日志。

选台时立刻生成新会话编号并取消旧的延迟恢复任务；旧源解析结果和旧错误不能更改当前状态。复用 Player 时，不能简单在回调里读取一个“当前会话号”就给所有事件贴上新标签；要结合绑定的 MediaItem 标识、事件时间线/媒体期，无法归属的旧事件丢弃。

进入播放后，`STATE_READY` 不代表电视已经显示首帧；首帧监听用于首帧统计，音频首声另测。自动保存“上次成功频道”在当前会话首帧后完成；如果先前成功频道在新的列表中消失，进入可操作频道列表而非反复打开失效地址。

| 事件 | 动作 | 终止条件 |
|---|---|---|
| 用户选了新频道 | 停止旧会话恢复/解析，切换媒体项并开始新会话 | 旧会话永不再接管 |
| 没有网络 | 显示简短状态，监听恢复；保留换台/返回操作 | 换台、退出立即取消；离线等待不堆积请求 |
| 暂时超时 / 可重试服务端错误 | 底层受限重试；预算内再重建本频道会话资源 | 有上层总时限和最大恢复次数，不因 prepare 又从零计数 |
| 401/403 | 按已知源协议最多刷新一次有效凭据/地址；无刷新能力则停止 | 不把重新使用相同凭据当作恢复；不遍历不相关地址 |
| 落后直播窗口 | 当前仍是普通直播且具有窗口时，返回默认直播位置再 prepare | 同一问题重复发生计入预算；回看/本地时移不自动跳走 |
| 不支持编码 / 解析失败 | 区分解码与容器；只尝试已确认有意义的替代配置 | 失败后给重试/选其他频道，不无限软硬切换 |
| 持续有声音但画面停止 | 结合渲染、解码和源数据判断，记录证据 | 不以画面像素不变直接判死流，静态镜头可以正常 |
| 播放恢复 | 清除临时提示；保留近期故障统计 | 不能一到 READY 就清空预算；稳定观察后才重置 |

恢复次数、等待上限和稳定窗口属于试验参数，见 `config/playback-evaluation.json`。普通直播与回看/时移模式分别保存策略，避免恢复逻辑破坏用户暂停的位置。

## 深入核实后的几个工程注意点

1. **重试阈值不是整个播放器的硬上限。** `DefaultLoadErrorHandlingPolicy.java:128` 给出重试延迟，`:139` 给出最少重试阈值；`upstream/Loader.java:289`、`:393` 明确是向上抛出错误前的阈值。不能只设这个值就声称整个应用最多恢复三次。
2. **直出 TS 与 HLS 里的 TS 配置入口不同。** 普通 TS 可由 `DefaultExtractorsFactory.setTsExtractorFlags` 设置；HLS 使用 `HlsMediaSource.Factory.setExtractorFactory` 与 `DefaultHlsExtractorFactory`。只改前者不代表 HLS 同样生效。
3. **缺少 H.264 AUD 的流可以评估 access-unit 检测。** `DefaultTsPayloadReaderFactory.java:84` 有该能力；允许 non-IDR 是另一开关，不全局打开。不能把 H.264 特定补丁应用到所有 HEVC 源。
4. **HLS 可在清单信息足够时省去初始分片探测。** `HlsMediaSource.java:292` 的 chunkless preparation 是条件能力，不是省略读取视频或预转码；清单声明不完整时仍需验证音轨/字幕是否识别正常。
5. **首播阈值和最大缓存分开。** 1.11.0 网络默认首播 1000ms、再缓冲 2000ms、加载上下界默认 50000ms；不能宣称默认要等 50 秒才出画。内存压力、字节预算和可用数据也会影响行为。
6. **HTTP 栈基线要一致。** `DefaultHttpDataSource.java:242` 的连接/读取默认超时均为 8 秒；这是一次网络操作的设置，不是用户感受到的总等待。首轮先用一个固定栈，不同时换网络栈、缓存值和解码方案造成原因不明。
7. **不要用增加延迟伪装“零卡顿”。** 自适应源记录可获得的 live offset；无公共时间基准的直出 TS 标明无法直接计算端到端延迟，必要时人工对齐同画面，不能填 0。

以上源码均相对 `reference/media3/media-1.11.0/libraries/`：播放核心在 `exoplayer/src/main/java/androidx/media3/exoplayer/`，HTTP 在 `datasource/src/main/java/androidx/media3/datasource/`，TS 在 `extractor/src/main/java/androidx/media3/extractor/ts/`，HLS 在 `exoplayer_hls/src/main/java/androidx/media3/exoplayer/hls/`。

## 试验顺序与通过标准

先保持上游默认参数得到基线，再一次只改一个因素：首播阈值、再缓冲阈值、特定源提取设置或特定设备解码选择。当前不把“快/稳/兼容”复杂模式暴露给老人，不预拉相邻频道，也不自动部署 NAS 转码。

第一轮实验参数清单仅用于样机开发和后续运行，不是实测成绩。真正的样例包括：正常 TS/HLS、无节目单、请求头必需、无文件后缀、慢首字节、短暂断片、持续断网、失效地址、快速连续选台。合成源只能证明这些路径，真实频道还需覆盖 1080i、50fps、HEVC、音频直通及源实际使用的组合。

对照组是 **kantv 的 Media3 实现、原版 TiviMate、Kodi**；不是 Media3 和新版 ExoPlayer 两份相同内核。相同设备、网络、地址与请求头，轮换测试顺序；受连接数限制的源不并发播放。记录版本、设置和源匿名编号。

分别测首帧 P50/P95、连续换台成功数、卡顿次数/累计时长、丢帧、音频 underrun、音画同步、直播延迟和资源趋势；不把视频帧提交回调完全等同于人眼屏幕出现时间。音画同步和电视外部显示延迟需人工或外部采集补充，客户端事件本身测不全。

进入第一版的最低行为要求：最终选台正确；旧错误不覆盖新频道；无 EPG 可播放；普通浮层不主动重连；自动恢复能终止；没有真实 URL/凭据日志。性能阈值先测基线再定。先前建议 30 次选台、两小时连续播放作为起点，仍不替代更长使用和兼容测试。

当前验收：资料/源码核实完成，方案与试验配置可审阅；未新增播放器代码和自动化播放测试；未构建 APK；未进行本轮模拟器或两台真机播放测试。
